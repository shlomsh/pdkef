# SIGN-18 · The Sign toolbar's per-row cap stopped matching when the Feedback control made it ten

## Scope and acceptance

**The Sign toolbar's per-row cap stopped matching when the Feedback control made it ten.** **Fixed by hiding Feedback below a 239px toolbar content box (a 336px viewport), approved as a product decision after the zoom implications were measured.** Two rules, and the split between them is the fix: the pre-existing `max-width: 251px` query is untouched and still serves nine-control toolbars, while a new `max-width: 239px` query hides `[data-optional-control]` *and* excludes it from its own counting selectors. They must stay separate. Between 239px and 251px Feedback is visible and must still be counted, or the three-way split fires on a toolbar showing ten and produces `3+3+3+1`; below 239px it is hidden and must not be counted, or the toolbar reads as ten and keeps the five-per-row share while nine render. `display: none` never changes `:nth-child(n of ...)`, which is what made the original bug invisible. `SignFeedbackButton.tsx` carries `data-optional-control="feedback"`; an attribute rather than a class because CSS Modules hash `styles.*` and the counting selectors have to name it, the same reason `[role="radiogroup"]` stands in for `.segmented`. **Verified by sweeping 280-440px: 335px and below give `3+3+3` with 57.9-76.2px targets, 336px and above give `5+5` with 44px+, every width balanced, and no hysteresis** (up-sweep, down-sweep and fresh loads agree exactly). The 12 toolbar tests pass, Redact is unaffected since it has no such control and the `:not(...)` is inert there. **Confirmed on Linux too** by CI run [33244247288](https://github.com/shlomsh/pdkef/actions/runs/33244247288) on `246c9f3`: all 12 toolbar cases pass on the runner and Playwright drops from 5 failures to 4, the remaining four being SIGN-19 alone. This one was not a platform-dependent failure, unlike those. **Two things worth keeping in mind if this is revisited.** Container queries match the CONTENT box, not the border box, so 239px content is a 336px viewport and 251px content is a 348px viewport; conflating them silently costs a 12px band, which is an iPhone SE 2nd/3rd gen at 110% zoom losing a control for nothing. And the band is not only 320px-class hardware: a current phone reaches it at roughly 115-125% browser zoom, and WCAG 1.4.10's 320px reflow case sits inside it, which is why hiding was only acceptable given the footer carries "Report a bug" and "Feedback & ideas" on every page. Do not apply `data-optional-control` to a control that edits the document. Original diagnosis, retained because it explains why the obvious fixes do not work: `e2e/sign/toolbar-touch-targets.spec.js` failed at 320px with rows reported as `4+3+2`. Pre-existing on `main` since `86913fe`, which added `SignFeedbackButton.tsx` and last touched `SignToolbar.module.css` in the same commit without re-tuning it; the spec was not in the focused Chromium set anyone had been running, so it went unnoticed. Measured at a 320px viewport: toolbar content box 223.2px, `gap` 4.8px, `--controls-per-row: 5`, so `flex-basis: max(44px, 20% - 3.84px)` floors at **44px** (the percentage branch computes 40.8px and loses), and `44*5 + 4.8*4 = 239.2px` does not fit 223.2px — only four controls per line ever do. The `@container toolbar (max-width: 251px)` rule that would drop the cap to `--controls-per-row: 3` is written as *exactly* nine (`:has(> :nth-child(9 of ...)):not(:has(> :nth-child(10 of ...)))`), and the toolbar now has ten non-excluded children (Text, Symbols, Shapes, Whiteout, Sign, Undo, **Feedback**, Full screen, Replace, Download, plus a `display:none` `[role=radiogroup]`), so it no longer applies and the cap stays at 5. **Re-tuning `--controls-per-row` cannot fix this, and that is the finding that matters.** With a 223.2px content box, a 4.8px gap and a 44px floor, at most four controls fit a line (`48.8n <= 228` gives `n <= 4.67`), and flex packs greedily, so ten controls wrap as `4+4+2` at a cap of 4, `3+3+3+1` at a cap of 3, and `4+4+2` at 5 (the cap never binds, the floor does). The balanced answer for ten is `4+3+3`, which greedy flex cannot produce at any cap. So **no value of `--controls-per-row` satisfies `max - min <= 1` for ten controls at 320px** while `--btn-min-size` stays at its WCAG 2.5.5 floor of 44px, which is not negotiable. The real fix is therefore a product decision about toolbar composition, not a CSS re-tune: get back to nine controls at this width by hiding a control the way `.desktop-download` already hides below 920px. **Feedback is the obvious candidate** — it is the one control that does not act on the document, and the design record's own label-drop reasoning ranks this app's editing vocabulary above ancillary controls — but that is a call about how visible the feedback channel should be on a phone, so it wants a human decision rather than a silent CSS edit. Note the CSS comment at `SignToolbar.module.css:173` still documents its hand-computed widths for "seven" and "nine" controls only; ten was never computed. **The affected width band is much narrower than "mobile", measured 2026-08-29 by sweeping 300-520px in 10px steps: only viewports below 336px are unbalanced.** At 336px and up the toolbar container clears 251px, the 44px floor stops binding, and all ten controls wrap as a clean `5+5`; the break is exactly where the container needs `44*5 + 4*4.8 = 239.2px` of content box, which happens at a 252px container, which happens at a 336px viewport. So the failing devices are **320px-class only**: iPhone SE 1st gen and the iPhone 5/5S/5C era, plus a folded Galaxy Fold outer screen at 280px. **Every iPhone Apple currently supports is unaffected** - SE 2nd/3rd gen are 375px, 12/13 mini 360px, 13/14/15/16 390-393px, Pro Max 428-440px - and all of them keep the Feedback control. Whatever hides it must therefore be scoped to the `@container toolbar (max-width: 251px)` band, **not** copied from `.desktop-download`'s 920px media query, which would strip it from every phone and tablet for no reason. **Option B simulated end to end at 2026-08-29 and verified green across the whole sweep:** 280/300/320/330px give `3+3+3` with 57.9/64.5/71.2/74.5px targets, and 336/340/375/390px give `5+5` with 44/44.8/51.8/54.8px targets. Note the counting selectors need the same treatment as `.desktop-download`: `display: none` alone does not re-arm the nine-control rule, because `:nth-child(n of ...)` counts DOM children regardless of rendering, so the hidden control must also be excluded in the `:not(...)` lists or the cap stays at 5. **The nine-control arithmetic was verified 2026-08-29, so the fix is known-good rather than hopeful:** drop to nine and the existing `max-width: 251px` rule matches again, sets `--controls-per-row: 3`, and `flex-basis` becomes `max(44px, (223.2 - 2*4.8) / 3) = 71.2px`, which packs as `3 * 71.2 + 2 * 4.8 = 223.2px` - exactly the content box, three per line, `3+3+3`, balanced, with a 71.2px touch target instead of 44px. **No CSS change is needed for that path; only the control count.** Second, independent bug: `readToolbar` in the spec maps `child.tagName === 'BUTTON' ? child : child.querySelector('button')`, and Feedback is an `<a class=button>` with no inner `<button>`, so the helper silently drops it and reports `4+3+2` where flex actually laid out `4+4+2` — the helper must count anchor controls too, or it will keep mis-describing whatever it finds. Do not "fix" this by relaxing the row-balance assertion.
