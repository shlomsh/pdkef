# Anonymous maintenance telemetry

PDkef processes PDF files, typed text, signatures, filenames, and saved drafts only in the browser. The hosted production site also uses Vercel Web Analytics for custom events. Every event is sent, with no sampling. Delivery is best-effort: offline browsers make no telemetry call, delivery failures are ignored, and no event is queued in browser storage.

There are two custom events. The first is `sign_export`. Its allowlisted fields are the outcome (`success` or `failure`), one coarse duration bucket (`under_1s`, `under_5s`, `under_30s`, or `30s_or_more`), and, only for failures, one stable error code (`unsupported_text`, `cancelled`, `invalid_document`, or `processing_failed`). The client never sends a PDF, bytes, filename, document or user ID, text, signature image, URL query/fragment, exception message, stack, or custom error fields.

The second is `sign_form_detection`, one event per document opened in the Sign tool, when the on-open form-field check finishes. Its allowlisted fields are the outcome (`success` or `failure`), one coarse count bucket on success (`none`, `one_to_five`, `six_to_twenty`, or `over_twenty`), and, only for failures, one stable error code (the four above, plus `modules_unavailable` for a detector whose own chunks never loaded and `not_started` for a run whose inputs were not all present, which throws nothing at all). It exists because a check that finds nothing and a check that never ran were indistinguishable from outside, which let a total detection failure ship unnoticed, and because a browser still being served a shell cached from before a deploy turns a working detector into a permanent silent zero. No field label, filename, page count, document text, page dimension, exception message, or raw field count is sent; the client cannot express them at this boundary. The captured exception itself never reaches telemetry at all: it is sanitised separately (`src/tools/sign/formDetectionDetail.ts`) for the person's own console and for the bug report they may choose to open.

Vercel Web Analytics is the reviewed transport. Its analytics documentation describes anonymous aggregate collection without cookies; the dashboard reporting window is plan-dependent (one month on Hobby, twelve months on Pro, and twenty-four months on Web Analytics Plus/Enterprise as of 2026-09-04). PDkef does not configure Analytics Drains, so these events have no additional destination. Reassess the provider, retention, event allowlist, and this disclosure before adding an event or changing a field.

## Anonymous error reports

Separately from the events above, when something in our own code breaks in a tool, the browser may send one small anonymous report to pdkef.com's own address, `/api/report`. It is a same-origin beacon POST, so `connect-src 'self'` is unchanged. The schema is `src/lib/errorReportSchema.ts`, the browser side `src/lib/errorReport.ts`, and the endpoint is `api/report.ts`.

A report holds: the area of the app that failed (one of a fixed list), the error's name (like `TypeError`), the chain of positions in our own published JavaScript that led there (up to 8, each a file name and line number), a short label our code gives the step it was doing (like `export` or `render_thumbnail`), the page's path (like `/sign/`, never a query or anything after it), whether PDkef is installed as an app, whether a service worker served the page, and roughly how long the page had been open (under 10 seconds, under a minute, under 10 minutes, or longer). It never holds the error's message, anything from a document, a filename, text, a signature, an IP address, or an identifier.

The server keeps daily counts of identical reports, plus the latest full example of each distinct error per day, with a coarse browser family and major version (like `ios-26` or `chromium-140`) taken from the request. They are stored in an Upstash Redis database connected to the project through Vercel, and deleted after 90 days. No IP address is stored.

Each distinct report is sent at most once per page load, and at most 10 per page. Nothing is sent when offline, a report never blocks or slows a tool, and failures are ignored.
