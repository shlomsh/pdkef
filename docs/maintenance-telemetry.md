# Anonymous maintenance telemetry

PDkef processes PDF files, typed text, signatures, filenames, and saved drafts only in the browser. The hosted production site also uses Vercel Web Analytics for page views only. Four tool lifecycle events (`tool_file_accepted`, `tool_operation_started`, `tool_result_ready`, `tool_operation_failed`, each carrying only the tool's name) and Sign's two maintenance events go to PDkef's own address, `/api/report`, the same one error reports use. Every event is sent, with no sampling, up to 20 Sign maintenance events and up to 40 lifecycle events per page, and the endpoint stops counting for the day past its daily cap of 1,000 for error reports and Sign events and a separate daily cap of 3,000 for the lifecycle events. Delivery is best-effort: offline browsers make no telemetry call, delivery failures are ignored, and no event is queued in browser storage.

There are two maintenance events. The first is `sign_export`. Its allowlisted fields are the outcome (`success` or `failure`), one coarse duration bucket (`under_1s`, `under_5s`, `under_30s`, or `30s_or_more`), and, only for failures, one stable error code (`unsupported_text`, `cancelled`, `invalid_document`, or `processing_failed`). The client never sends a PDF, bytes, filename, document or user ID, text, signature image, URL query/fragment, exception message, stack, or custom error fields.

The second is `sign_form_detection`, one event per document opened in the Sign tool, when the on-open form-field check finishes. Its allowlisted fields are the outcome (`success` or `failure`), one coarse count bucket on success (`none`, `one_to_five`, `six_to_twenty`, or `over_twenty`), and, only for failures, one stable error code (the four above, plus `modules_unavailable` for a detector whose own chunks never loaded and `not_started` for a run whose inputs were not all present, which throws nothing at all). It exists because a check that finds nothing and a check that never ran were indistinguishable from outside, which let a total detection failure ship unnoticed, and because a browser still being served a shell cached from before a deploy turns a working detector into a permanent silent zero. No field label, filename, page count, document text, page dimension, exception message, or raw field count is sent; the client cannot express them at this boundary. The captured exception itself never reaches telemetry at all: it is sanitised separately (`src/tools/sign/formDetectionDetail.ts`) for the person's own console and for the bug report they may choose to open.

The Sign events are sent as a same-origin beacon and counted by the endpoint in the same Upstash Redis database as error reports, as daily counts by browser family and version (like `ios-17` or `chromium-140`), with no sample, no IP address and no full user agent, and deleted after 90 days. They count toward the same daily cap as error reports. `npm run errors:read` prints them under "Sign maintenance events".

The four lifecycle events are also sent as a same-origin beacon to `/api/report`, and are kept as daily counts per event and tool (no browser family, no sample, no IP address), deleted after 90 days, under their own daily cap of 3,000. `npm run errors:read` prints them under "Tool usage".

Vercel Web Analytics is the reviewed transport for page views only. Its analytics documentation describes anonymous aggregate collection without cookies; the dashboard reporting window is plan-dependent (one month on Hobby, twelve months on Pro, and twenty-four months on Web Analytics Plus/Enterprise as of 2026-09-04). PDkef does not configure Analytics Drains, so page views have no additional destination. Reassess the provider, retention, event allowlist, and this disclosure before adding an event or changing a field.

## Anonymous error reports

Separately from the Sign events above, when something in our own code breaks in a tool, the browser may send one small anonymous report to pdkef.com's own address, `/api/report`. It is a same-origin beacon POST, so `connect-src 'self'` is unchanged. The schema is `src/lib/errorReportSchema.ts`, the browser side `src/lib/errorReport.ts`, and the endpoint is `api/report.ts`.

A report holds: the area of the app that failed (one of a fixed list), the error's name (like `TypeError`), the chain of positions in our own published JavaScript that led there (up to 8, each a file name and line number), a short label our code gives the step it was doing (like `export` or `render_thumbnail`), the page's path (like `/sign/`, never a query or anything after it), whether PDkef is installed as an app, whether a service worker served the page, and roughly how long the page had been open (under 10 seconds, under a minute, under 10 minutes, or longer), and `actions` (DEBT-31): the last up to 10 things the person did in the tool, oldest first, as names from the closed list `ACTIONS` in `src/lib/errorReportSchema.ts` (`add_files`, `replace_file`, `remove_file`, `clear_all`, `open_recent`, `undo`, `redo`, `reorder`, `sort`, `rotate`, `hide_page`, `delete_page`, `select_pages`, `change_setting`, `arm_tool`, `place_mark`, `move_mark`, `resize_mark`, `edit_mark`, `delete_mark`, `draw`, `detect_fields`, `fill_field`, `zoom`, `fullscreen`, `export`, `download`, `share`). A repeat of the last name is dropped, so a drag cannot push the history out of the ring of `MAX_ACTIONS` (10). Names only: no file name, count, position, text or anything from a document. The trail (`src/lib/actionTrail.ts`) lives in memory for the life of the page and is read only when an error is reported. It never holds the error's message, anything from a document, a filename, text, a signature, an IP address, or an identifier.

The server keeps daily counts of identical reports, plus the latest full example of each distinct error per day (including its `actions`), with a coarse browser family and major version (like `ios-26` or `chromium-140`) taken from the request. They are stored in an Upstash Redis database connected to the project through Vercel, and deleted after 90 days. No IP address is stored.

Each distinct report is sent at most once per page load, and at most 10 per page. Nothing is sent when offline, a report never blocks or slows a tool, and failures are ignored.
